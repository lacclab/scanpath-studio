How this tracker works

Every item has a stable ID you can cite in chat ("let's do CMP-3"), a status, and a short write-up with code anchors. Expand an item to change its status or leave implementation instructions. Changes are saved directly into tracker/state.json; the original catalogue stays in tracker/data.js.

Editing tasks

  • Expand a task, choose a status, and describe the outcome, constraints, or acceptance checks in Instructions for implementation. These are saved in the repository and become the task handoff for whichever coding agent works next.
  • Use New task to capture work without editing the catalogue by hand.
  • Start the live tracker by double-clicking tracker/start.command, or run python3 tracker/server.py. Keep that terminal window open.
  • Each save writes to the project immediately. No downloads or file permissions are involved, and concurrent browser tabs are protected from overwriting each other.
  • Closed archives an item automatically. Moving it to any active status restores it to the open list.

Status

  • Backlog — captured, not scheduled.
  • Planned — scoped and intended as upcoming work.
  • In progress — actively being implemented.
  • On hold — intentionally paused or waiting on something.
  • Review — implemented and waiting for your sign-off.
  • Closed — finished or no longer active; it is archived automatically.

Write-up shape

Four bold-led paragraphs, in this order, so the ask stays legible next to what shipped (there are no headings — the renderer is deliberately tiny):

  • Request — what was asked for, in the asker's terms.
  • What was done — what actually shipped.
  • What's left — what remains. Say it either way, and link the follow-up item when the remainder was split out. An item in Review is never "Nothing" — what is left is your review, so name what to look at. "Nothing" is for an item that is genuinely finished and signed off.
  • Background (technical) — code anchors, design calls, gotchas, related IDs. The internal half, kept out of the first three.

Open questions do not live in Background. They go in a separate decisions field — a list of the calls that need your input before the work can start. They render as their own amber box at the top of the item, put a ⚖ to settle badge on the card, and are what the Waiting on my decision filter collects. Answer them in Instructions for implementation; whoever implements clears the field and records the call in Background.

An item with no implementation behind it has only Request (plus Background), whether it is Backlog, Planned, or On hold. The other two appear once work exists. An implemented item keeps its status line as the leading > quote.

Rules

  • Approval gate. When implementation is finished, mark it Review — never jump straight to Closed. Only after the user signs off does it become Closed + archived: true. Work closed without implementation should say why in its instructions or write-up.
  • IDs are stable. Never renumber. New items take the next free number in their prefix (see below); archived items keep their ID.
  • Composite asks are split into sub-items so they can land independently.
  • When implementing an item, ask for clarification as needed before starting.
  • When any view, measure, severity, or path here lands, update AGENTS.md, scanpath_studio/CLAUDE.md, CHANGELOG.md and the docs/ site in the same change.
